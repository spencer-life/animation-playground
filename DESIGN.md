# Design System: Animation Playground

## Overview

**Creative North Star: "The Material Sample Rack"**

The Material Sample Rack gives small motion studies the clarity of objects laid out for close inspection. The surrounding workspace is cool, quiet, and matter-of-fact: graphite type on paper surfaces, solid neutral selections, clear control outlines, and generous sample fields. Precision belongs to the tools; warmth and individual character belong to the examples.

Inter supplies a consistent working voice, with system monospace reserved for code and motion values. Rounded rectangles feel handled and practical. Tonal separation carries most of the hierarchy. Playground colors preserve each study's lavender, apricot, blue, green, sand, or graphite family in light and dark compositions. Radix, Geist-inspired, and custom-accent palettes let the demonstrations take on a project's colors. Their appearance can follow the site or use an explicit light or dark mode.

Keep the shared tools still and responsive. Motion belongs inside studies that people choose to inspect, replay, or slow down. Expressive type and playful shapes can be part of a study; the shell remains readable and consistent. Reduced-motion states preserve visible content and understandable state.

**Key Characteristics:**

- Cool paper surfaces, graphite text, neutral solid selections, and outlined controls.
- Compact, legible tools around generous sample stages.
- A shared semantic palette colors the live demonstration and the implementation taken from it.
- Inter for the interface; system monospace for source and precise values.
- Flat containers, restrained rounding, and small functional shadows.
- Immediate navigation with deliberate, controllable motion inside examples.

This specification records the shared values in [the shell stylesheet](src/styles.css), [the rendered interface](src/app.js), [the shared demo styles](src/demo-base.css), and [the theme resolver](src/theme.mjs). [Gallery playback](src/gallery-playback.js) and [the demo runtime](src/demo-runtime.js) define the preview lifecycle. The YAML owns the documented shell primitives and resolved default demonstration values. The resolver is canonical for the complete palette and appearance matrix; [the theming guide](docs/theming.md) records its integration contract. The sidecar extends the frontmatter with preview components and metadata; its synthesized tonal ramps are panel display aids, not additional implementation tokens.

## Colors

The palette combines cool neutral tools with sample material that can adapt to the receiving project. Shell colors and demonstration colors have separate scopes. Preserve the source formats in the frontmatter and use the existing CSS variables within the appropriate scope.

### Primary

- **Graphite ink** (`ink`) with **Paper surface** (`surface`) identifies primary actions and selected navigation, collection, playback, icon, and segmented controls. The same roles reverse with the shell theme; labels, counts, and icons remain readable on the solid fill.
- **Cobalt control accent** (`accent`) remains for links, the three-bar brand, text selection, and keyboard focus. **Night cobalt** (`dark-accent`) supplies the dark-theme value.
- Ordinary actions and native selects use neutral outlines. The declared shell `accent-soft` values are not used as control fills; demonstration soft colors retain their independent, intentionally limited uses.

**The Shell Control Rule.** Use solid neutral selection and clear neutral outlines for the shared workspace. Do not reintroduce tinted selected buttons, navigation washes, or soft-filled utility controls. Keep the accent for focus and useful small cues, and keep focus distinct from selection.

### Secondary

These are the six light sample fields in the original Playground palette. Keep their incumbent keys: `peach` remains the source key even though its descriptive name is apricot. Each has a corresponding dark composition derived by the shared resolver.

| Token | Descriptive name | Use |
| --- | --- | --- |
| `lavender` | Muted lavender | Soft violet sample material; the default stage fallback. |
| `peach` | Muted apricot | Warm interaction, text, and gesture studies. |
| `blue` | Powder blue | Cool spatial, progress, and numeric studies. |
| `green` | Pale green | Calm card, state, and layout studies. |
| `sand` | Warm sand | Neutral warm material for timing and navigation studies. |
| `graphite` | Pale graphite | Neutral cool material for typographic and control studies. |

Recipe metadata chooses the family in Playground colors; category alone does not determine it. The stage uses the resolved `--demo-bg`, including when a project palette is selected. Its generous area, clipped edge, and open caption continue to separate the demonstration from the shell in either appearance.

**The Sample Material Rule.** Preserve each recipe's family in Playground colors, including its mode-appropriate dark composition. Project palettes may recolor the whole demonstration. Keep the shell's navigation selection and application status meanings separate from these palette choices.

### Demonstration palettes and roles

| Palette | Visual contract |
| --- | --- |

The project accent choices are Indigo, Blue, Violet, Jade, Amber, and Crimson. Their solid swatch values are the `palette-*` frontmatter entries; `palette-custom` records the initial custom input. These are demonstration choices, not new shell action colors. Light and Dark are explicit demonstration appearances. Match site resolves to the current shell appearance without changing the selected palette or original family.

The `demo-*` frontmatter colors record the resolver's Original/lavender/light values; `demo-dark-*` records the corresponding dark values. These are documented defaults, not a second implementation of the palette matrix. Except for `demo-bg`, the documentation prefix distinguishes a demonstration role from a shell token with the same name: `demo-paper` maps to `--paper`, `demo-accent` to `--accent`, and so on inside the demonstration.

| Semantic role | Use |
| --- | --- |
| `--demo-bg`, `--paper` | The study canvas and its component or panel surfaces. |
| `--ink`, `--on-ink`, `--muted` | Primary text, the foreground on ink-filled controls, and secondary readable text. |
| `--line` | Boundaries, tracks, and separators. |
| `--accent`, `--accent-hover`, `--accent-soft` | Solid accent fills, their hover state, and quiet supporting fills. |

**The Shared Color Contract Rule.** Resolve demonstration surfaces, text, controls, and artwork through the same semantic roles in previews, standalone examples, copied code, downloads, and AI handoffs. Use `--accent-ink` for readable accent text and focus, `--on-accent` over solid accent fills, and `--on-ink` over ink fills. Validate accent text at 4.5:1 against paper, canvas, and soft accent surfaces, and retain the corrected foreground in host-token exports. Keep raw palette values in the shared resolver.

Full examples embed the selected concrete colors and appearance for offline use. A copied Match site appearance resolves to its current light or dark value. Token exports use a dedicated `.animation-theme` wrapper: standalone values reproduce the preview, Radix aliases map neutral surfaces and accent fills, and Geist aliases map only neutral roles. Accent text and solid foregrounds retain their resolved literal values. Host aliases take precedence over the exported fallbacks; the receiving theme supplies its active scales and remains responsible for the resulting foreground contrast. The precise alias table and scope requirements belong in [the theming guide](docs/theming.md).

### Tertiary

- **Category markers** use the six `category-*` tokens for feedback, navigation, layout, text, entrances, and expressive work. Their muted small dots help scan the collection; labels and counts carry the information.
- **Source syntax** uses `code-string`, `code-keyword`, and `code-number`, with the matching `dark-*` values in the dark inspector. These are technical reading aids, not additional action colors.

### Neutral

- **Cool paper** (`bg`) is the full workspace canvas and rail. **Paper surface** (`surface`) is the input surface on mobile, the button surface, and the inspector or specifications panel.
- **Inset grey** (`subtle`) supports static technology tags. **Graphite ink** (`ink`) is the primary reading color and solid-control fill; neutral hover surfaces mix ink with the shell surface.
- **Slate text** (`muted`) carries descriptions, inactive counts, explanatory metadata, and readable neutral field boundaries. **Cool divider** (`faint`) separates navigation groups, source tabs, tables, and footers.
- **Code paper** (`code`) is the source and agent-brief surface. **Comment slate** (`code-comment`) keeps comments secondary while preserving readability.
- The `dark-` tokens record the actual overrides of these same variables. In implementation, switch the root theme and continue using the original variable names; do not hard-code dark values into individual components.

## Typography

**Display and body font:** Inter, followed by the system sans-serif fallbacks in the frontmatter. The app serves the variable font locally.

**Code font:** SFMono-Regular, Consolas, Liberation Mono, then monospace. Source panes use the operating system’s available member of this stack.

**Character:** Neutral, compact, and attentive to small differences. Headings use modest negative tracking and slightly stronger weights; labels remain plain sentence case. The system has an observed role scale rather than a uniform mathematical ratio.

- **Display** (`display`) remains the general page and notes heading. Its wide-layout size is (42px), with a medium-heavy variable weight (620) and tight line height (1.15). - **Sample title** (`sample-title`) is compact and semibold at (14px), followed by **Sample description** (`sample-description`) at (12px) with a line height of (1.65). **Sample metadata** (`sample-metadata`) uses (11px), becoming (10px) in the narrow phone layout. Related studies retain their compact local title treatment.
- **Body** (`body`) is the base interface text. **Intro** (`intro`) adds a more open reading rhythm for short page introductions. The discovery introduction extends the general (455px) measure to (610px) on wide screens, becoming (55ch) at the mobile breakpoint.
- **Navigation** (`navigation`) and **label** (`label`) support category rows and utility buttons. Small technology tags use `tag`; metadata uses `metadata`. Counts and numeric results use tabular figures where shown.
- **Code** (`code`) uses a compact size (12px) with an open line height (1.85), becoming (11px) at the mobile breakpoint. Long source lines scroll within the source pane; explanatory copy wraps normally. Gallery descriptions use a measure of (42ch), extending to (48ch) on narrow phones.

Collection and intent buttons reuse the existing label role; the native discovery selects use the regular-weight **Discovery input** (`discovery-input`) role.

**The Working Type Rule.** Use the shared Inter stack for interface hierarchy and the system mono stack for code. Expressive display treatments belong to individual demonstrations.

## Layout

The main region has a maximum width of (1600px). Its normal horizontal padding is (38px); the rail width is (222px).

The gallery uses three equal columns with separate row and column gaps (30px and 22px). Each sample is a colored, clipped stage followed by an unenclosed caption. At rest, the stage height is (232px). Preserve the distinction between generous demonstration space and compact tools; do not force all spacing into a newly invented base grid. The frontmatter includes recurring literal steps, including optical offsets such as (13px), (18px), (22px), and (38px).

The study workbench pairs a demonstration with the source inspector using near-equal columns (1.03fr and 1fr) and a shared gap (22px). Its main stage is (400px) tall at the standard wide size. Motion specifications are a two-column definition list beneath the demo controls. Notes use a narrower reading region (900px) with two columns of principles.

The color controls use a four-column grid with a gap of (14px), inside a surface with padding of (18px 20px). The summary remains a generous disclosure target with a minimum height of (44px). These tools use the existing flat surface and compact control vocabulary.

## Elevation & Depth

## Do's and Don'ts

### Do:

- Do keep the shell’s background, surfaces, text, selection colors, and source colors bound to the current theme.
- Do preserve each study's original color family in Playground colors and resolve its light or dark composition through the shared theme system.
- Do carry the same selected demonstration colors into live previews, copied code, standalone downloads, and AI handoffs.
- Do use readable accent and solid-foreground roles for demonstration text and focus, with scoped token exports when adapting a study to a host theme.
- Do use Inter for interface copy and system monospace for source and exact motion values.
- Do keep category changes, search, keyboard navigation, and source-tab changes immediate.
- Do give each sample a generous clipped stage with its name, concise explanation, technology, duration, and intent below.
- Do keep project collections, native filters, and the color disclosure within the existing quiet control vocabulary.
- Do retain visible keyboard focus, readable labels, and a coherent reduced-motion state.
- Do use the existing responsive grid and horizontal mobile category strip before inventing a new navigation pattern.

### Don't:

- Don't add ornamental gradients, glow, or unnecessary marketing decoration to the shared workspace.
- Don't use soft accent fills for shell controls or replace a selected solid treatment with a pale hover wash.
- Don't add animation to the navigation or make repeated utility actions wait for a transition.
- Don't confuse shell selection colors with the selected demonstration palette, or force studies to stay light when a dark appearance is chosen.
- Don't hard-code recipe colors or let exported color values diverge from the live demonstration.
- Don't assume host token aliases preserve foreground contrast after the receiving theme changes its scale or appearance.
- Don't surround every sample with an extra border, shadow, or enclosing card surface.
- Don't hide essential meaning behind hover, playback, or spatial movement.
- Don't treat an individual recipe’s expressive colors, type, shadows, or timings as universal shell tokens.
